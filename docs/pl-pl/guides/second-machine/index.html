    Zbieranie na drugiej maszynie¶

    Całe źródło to setki tysięcy próśb i dni pracy, więc ciężkie pobieranie może być uruchomione na innej maszynie, z danymi na dysku zewnętrznym. Ta strona mówi, jak to skonfigurować tak, że działa na dowolnym Linuksie (w tym Parrot OS) i na dowolnym dysku, i jak sprawdzić, co wraca. Jak dane podróżuje do domu jest nadal otwarty (Q10 w devlog); oba sposoby są opisane.

    Układ, który działa na dowolnym dysku¶

    Co? Gdzie Dlaczego?
    Kopia robocza oraz node_modules własny dysk maszyny, e.g. ~/__WORKSHOP/forge/sarverott/P-jol-roll npm wymaga dowiązania symultanicznego i plików wykonywalnych, których dyski exFAT i NTFS nie utrzymują, a dyski wyjmowane są zazwyczaj montowane noexec
    Bezstronne repozytorium (opcjonalne) napęd zewnętrzny prosty pilot zdalny: git clone /media/<you>/<drive>/P-jol-roll.git; git tylko czyta i pisze obiekty
    Zebrane dane napęd zewnętrzny, przez RESOURCES_DIR dużych plików, napisane w całości (.part pierwszy), nic w nim jest nigdy uruchomić 
    # on the second machine
git clone https://github.com/Sarverott/P-jol-roll.git ~/__WORKSHOP/forge/sarverott/P-jol-roll
cd ~/__WORKSHOP/forge/sarverott/P-jol-roll
npm install                                   # Node 24, npm 11 (.nvmrc)
mkdir -p /media/$USER/<drive>/p-jol-roll-resources
cp resources/.map.json resources/frontends.json /media/$USER/<drive>/p-jol-roll-resources/
echo "RESOURCES_DIR=/media/$USER/<drive>/p-jol-roll-resources" >> .env
task check                                    # nothing asks the internet
task gather -- 2026 --acts --limit 5          # a small run first

    .env.example wymienia wszystkie ustawienia; każde zadanie czyta .env kopii roboczej (dotenv w Taskfile.yml), więc RESOURCES_DIR tam znajduje się dla nich wszystkich; zmienna ustawiona w powłoce wygrywa nad nią. npm run ... bez zadania nie odczytuje .env: tam, eksportuj najpierw zmienną. .env jest ignorowany przez git.

    Kiedy coś odmawia¶

    Co widzisz? Przyczyna Co robić
    fatal: detected dubious ownership in repository git odmawia repozytorium, którego pliki należą do innego użytkownika; na exFAT i NTFS każdy plik wydaje się należeć do tego, kto zamontował dysk git config --global --add safe.directory /media/<you>/<drive>/P-jol-roll.git dla tej jednej ścieżki; lepiej, zachować kopię pracy na dysku wewnętrznym
    npm install nie EPERM lub symlink błędy system plików napędu nie posiada żadnych linków (exFAT, FAT32) zainstalować na wewnętrznym dysku (układ powyżej)
    Permission denied kiedy haczyk, tsx lub task działa napęd jest zamontowany noexec (findmnt -o TARGET,OPTIONS <path> Pokazuje to) nie uruchamiać niczego z napędu; tylko dane tam mieszka
    nie task binarne po npm install npm 11 skips zainstalować skrypty, które nie są zatwierdzone package.json zatwierdza @go-task/cli w allowScripts; jeśli został zainstalowany ręcznie ze starszą kasą, uruchomić npm install ponownie
    haki nie zatrzymują złego commit @go-task/cli powyżej 3.54 upuszcza kod wyjścia npm install z tej wersji repozytorium przynosi 3.54

    lsblk -f pokazuje jak dysk jest sformatowany, findmnt <path> jak jest montowane. task unittesting:parrot-os-drive pokazuje trzy odmowne powyżej na Parrot OS z zamontowanym napędem FAT noexeci układ tej strony pracujący na tym samym dysku.

    Odzyskanie danych¶

    Druga maszyna zbiera, potem uszczelnia, więc każdy plik ma zapis sumy kontrolnej w dataset/files/:

    task seal            # records for anything gathered without one
task seal -- --check # reads every file again, names any that differ

    Następnie jeden z dwóch sposobów (Q10):

    • Pcha do samego Hugging Face., z symbolem właściciela w .env: task resources:push -- bucket, task resources:push -- datasetHome machine bierze go z task resources:pull -- dataset (oraz bucket gdy chce surowe pliki), wtedy task seal -- --check.
    • Napęd jedzie do domu.: punkt RESOURCES_DIR tam, biegnij task seal -- --checkA potem pchać z domu.

    Tak czy inaczej, plik z rekordem nie jest ponownie proszony, więc dwie maszyny, które udostępniają zbiór danych nie zbierają tych samych plików dwukrotnie. Podziel pracę według dziennika lub według lat (task gather -- 1990 1991 --acts --limit 0 --publisher MP) gdy obie maszyny zbierają się natychmiast.
