    Understood as:

    • The corner. Every host of the viewer that has the api says what it is in a fixed corner: v<release> · <short name>, the short name made of where it runs (HF-demo, remote, local), whether it writes (readonly, writing) and container. A hover, a focus or a touch shows the whole note under it, at most as wide as the screen: the release, a container or not and production or not, where its data comes from, read-only or writing and who built it (the workflow's run), the commit. The corner keeps one size whatever it says, and the note takes no pointer, so the note can never cover the corner. The api says it at /api/host; the release gives the image its commit and run.
    • Phases ahead. The milestones are read again and the phases of M4 and M5 still undetermined are planned from the owner's own words (Q17, Q18, PP4, the milestones of ROADMAP) - planned, not started.
    • GitHub's own places. Yes: the milestones of ROADMAP become milestones of the repository; every phase an issue in its milestone, closed when its TODO is ticked; every Q<n> and PP<n> an issue, closed when answered or decided; all of them on a project board (kanban). The markdown stays the source; a task brings it there again whenever it changes.
    • The wiki is a git submodule of this repository and holds a copy of the devlog and the almanac, made by a task - the files here stay where they are.
    • The language packs come from their gist, a submodule at resources/locales: the source the project reads, opposite to the wiki.
    • The documentation (Read the Docs) no longer publishes the devlog and the almanac; its list of contents links to them in the wiki.
