    Entwicklung¶

    Wie man den Code ändert. Wie man eine Änderung vorschlägt, siehe BEITRAG.

    Der Code¶

    Datei Was ist in ihm
    src/core/main.ts Argumente und Befehle. Die Verwendung wird an der Spitze geschrieben
    src/core/apihandlers/eli.ts die API: ihre Adresse, Formen der Antworten, Adressen jedes Teils einer Handlung
    src/core/resources/store.ts Wo gesammelte dinge geschrieben werden und wie..part, dann Umbenennung
    src/core/crawl.ts ein höflicher Spaziergang über Adressen einer API: eigener Name, Tempo, Schlange im Gedächtnis
    src/core/methods/gather.ts Index → Listen → Jahre, dann Akten von Jahr zu Jahr; --since für Änderungen
    src/core/methods/seal.ts Checksummen der gesammelten Dateien: Aufzeichnungen schreiben, Dateien gegen sie prüfen
    src/core/methods/compile.ts Detailtabellen und Referenzen aus Rohdateien
    src/core/parsing/text.ts markdown von HTML, mit Aufzeichnungen, die beide binden
    src/core/apihandlers/sejm.ts eine weitere Quelle: Prozesse und Drucke von Sejm
    src/core/apihandlers/saos.ts Eine weitere Quelle: Gerichtsurteile
    src/core/methods/checkup.ts der Browser, der Webseiten besucht, mit Crawlee PlaywrightCrawler und Camoufox
    src/core/resources/hub.ts Vergleich und Synchronisierung mit Hugging Face, mit @huggingface/hub

    Vier Regeln halten es lesbar:

    • Adressen und Daten bleiben den Handlern fern. Ein Handler in gather.ts sagt, was passiert; wo zu fragen ist in eli.ts und wo zu schreiben ist in store.ts.
    • Ein Kommando, eine Datei. main.ts Lesen Sie nur Argumente und Anrufe.
    • Kein Flat Scope. Dateien sitzen im Verzeichnis ihrer Art unter src/core/: apihandlers/ für Quellen, methods/ für das, was Befehle tun, parsing/ für Rohdateien in Text, resources/ für die lokalen Seiten und Hugging Face. Eine neue Art erhält ein neues Verzeichnis.
    • Typen und Schnittstellen leben in src/core/vars/. eine pro Datei, types/<Name>.type.ts oder interfaces/<Name>.interface.ts, mit einem Standardexport und keine Verzeichnisse innerhalb. Die index.ts von jedem Verzeichnis setzt sie in Namespaces, GatheringScope und HuggingfaceScope, und Code nimmt sie von dort:
    import type { GatheringScope } from "../vars/interfaces/index.js";
import type { GatheringScope as GatheringTypes } from "../vars/types/index.js";

function trusted(act: GatheringScope.Act, part: GatheringTypes.Part) {}

    src/cli-command.js, src/cli-repl.js, src/desktopapp/, src/webgui/ und src/webserver/ sind Anfänge anderer Wege in den gleichen Kern. Sie sind noch nicht an irgendetwas gebunden.

    Aufgaben¶

    Aufgabe Was es tut
    task lint Biome: Flusen und Formatierung, ändert nichts
    task format Biom mit sicheren Fixes
    task build TypeScript in dist/Die Website in dist/web
    task test Tests, einmal
    task check oder task verify) Flusen, Bau und Tests - das gleiche wie CI. Führen Sie es aus, bevor Sie die Arbeit als erledigt melden
    task seal, compile, text Arbeiten an gesammelten Dateien, ohne Internet: siehe Verarbeitung
    task github:repo, runs, issues, prs Lesen Sie den Zustand des Repositorys auf GitHub mit gh

    Jedes Verzeichnis mit Prozeduren hat seine eigene Taskfile.yml (.husky, .github, resources), in der Wurzel eins enthalten.

    Prüfungen¶

    Vitest, tests/Sie berühren nie die echten API, die Webseiten oder Hugging Face.

    Datei Was es überprüft
    eli.test.ts Wahl der Zeitschriften und Jahre, Adressen, Pfade der Dateien
    gather.test.ts ganze Versammlungen gegen eine lokale Kopie der API: Listen, Ordnung, Limit, Überspringen, was existiert, Aufzeichnungen, Struktur und andere Texte, Änderungen seit einem Tag; dann Tabellen, markdown und Prüfsummen aus dem Ergebnis
    sources.test.ts Sejm und Urteile gegen lokale Kopien ihrer APIs
    checkup.test.ts wie Adressen von Websites aus einer Handlung ausgefüllt werden
    hub.test.ts Benennung von Repositories, und dass nur das, was sich unterscheidet, bewegt wird

    Ein Test, der den API benötigt, startet einen kleinen Server und zeigt den Code darauf:

    process.env.ELI_API = `http://localhost:${port}`;
process.env.RESOURCES_DIR = join(work, "resources");
process.env.CRAWLEE_STORAGE_DIR = join(work, "storage");

    Diese müssen gesetzt werden, bevor der Code importiert wird, denn eli.ts und store.ts Lesen Sie sie einmal.

    Hinzufügen einer weiteren Datei pro Akt¶

    Zum Beispiel structdie der API als /acts/DU/2026/1/struct:

    1. src/core/apihandlers/eli.ts: Fügen Sie den Namen hinzu PARTS und eine Zeile zu filesOf, mit der Adresse, unter der es gefragt wird, und dem Ende seines Dateinamens. Wenn die Datei nicht für jede Handlung existiert, geben Sie nichts für die Handlungen ohne sie zurück.
    2. tests/gather.test.ts: Lassen Sie die lokale Kopie des API darauf antworten.
    3. docs/guides/data.md, docs/guides/gathering.md und die Tabelle in AGENTS.md.

    gather.ts und seal.ts brauchen sich nicht zu ändern: eine Datei endet in .json wird als JSON gespeichert, einer endet in .pdf Es muss ein PDF sein, und alles andere bleibt so, wie es kam. Dies ist, wie struct wurde hinzugefügt.

    Hinzufügen einer Website zum Checkup¶

    Ein Eintrag in resources/frontends.json. Lesen Sie die Website robots.txt zuerst und schreiben, was es sagt in title wenn es die Crawler verbietet.

    Hinzufügen einer Quelle¶

    Eine weitere API ist eine weitere Datei mit ihren Adressen, Formen und Sammeln und einem Befehl in main.ts; sejm.ts und saos.ts Das sind die Beispiele. crawl.ts gibt den höflichen Spaziergang, store.ts das Verfassen von Akten und hub.ts die Bewegung. Ihre Verzeichnisse sind resources/<source>-dataset und resources/<source>-bucketVorschlagen Sie es zuerst mit dem "new source"-Ausgabeformular; bereits geprüfte Kandidaten sind in Ideen.

    Stil¶

    Biome entscheidet: Tabs, doppelte Zitate, sortierte Importe. package.json hält Räume. .obsidian/ nicht überprüft wird. Der Pre-Commit-Hook führt Biome auf inszenierten Dateien durch .husky/Taskfile.yml.

    Kommentare sind kurz und sagen warum. // NOTE: Kommentare sind Aufgaben des Maintainers, mit ANSWER: Zeilen als Antworten; beide bleiben.

    Bilder, Icons, die Karte eines Links¶

    Die Bilder des Projekts leben in einem gist des Eigentümers, MEDIAFILES, als Submodul eingebunden resources/mediafiles. task resources:media (ffmpeg) macht, was Seiten aus ihnen brauchen, und die Ergebnisse sind verpflichtet, so dass kein Build ffmpeg oder das Submodul benötigt:

    hergestellt von In
    favicon.ico, favicon-16/32/48.png Luchskopf lex-polonis.png src/web/public/
    apple-touch-icon.png, icon-192.png, icon-512.png, icon-maskable-512.png das Ganze lex-polonis.png (256 Farben) src/web/public/, benannt in src/app/manifest.json
    og.jpg, 1200x630 p-jol-roll_edited-color.png src/web/public/
    favicon.png, logo.png Der Luchskopf docs/assets/images/ (MkDocs)
    icon-48/96/128.png Der Luchskopf src/firefox-ext/icons/

    Der Betrachter (src/web), die Einführung (webpage/, seine publicDir ist src/web/public) und die Dokumentation (docs/_mkdocs/overrides/main.htmltragen das Favicon, theme-color und die Open Graph-Karte, also ein Link, der auf Social Media-Shows geteilt wird og.jpg.
